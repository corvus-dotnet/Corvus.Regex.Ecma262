# Plan: phase 6 for .NET

Corvus.Text.Json takes Corvus.Regex.Ecma262 in place of its translator to `System.Text.RegularExpressions`, for
`pattern`, `patternProperties` and `format: regex`, in generated code and in the runtime evaluator. It is the first
of the phase 6 pull requests ([the plan for every port](engines-for-every-port.md), step 7); Rust, Go, Java,
Pascal, OCaml, Python and Julia follow, one at a time.

## 1. What changes today's behaviour

- **Answers.** Today a pattern is translated to .NET's syntax (`EcmaRegexTranslator`), with ECMA-262's meaning
  approximated where the two differ, and run by .NET's engine over UTF-16, so every UTF-8 string is transcoded
  first. After this, a pattern is ECMA-262's, run over the UTF-8 bytes as they are, with the answers of the test
  data (none wrong in 30,022,246).
- **Generated code.** The Corvus source generator emits `new Regex(translated, RegexOptions.Compiled)`, since a
  source generator does not run on another's output and `[GeneratedRegex]` inside generated code is never
  expanded. The CLI emits .NET's `[GeneratedRegex]` on .NET 8 or later. After this, both emit the compiled matcher
  itself, as Corvus.Regex.Ecma262's source generator writes it, so a source-generated type has generated code too.

## 2. Three pull requests

**A. Corvus.Regex.Ecma262: the emitter as a source package.** A new package,
`Corvus.Regex.Ecma262.CodeGeneration.Sources`, which carries the emitter's C# files (the parser, the compiler and
the two emitters, the files the source generator links today) as source compiled into the project that takes it,
with no assembly. A source generator takes it with `PrivateAssets="all"` and compiles the emitter into itself, so it
loads no library beside it. Its types are `internal`, so two projects that take it never clash. It has one entry:

```csharp
internal static bool TryEmit(
    string pattern, RegexFlags flags, RegexEdition edition, RegexUnicodeVersion unicodeVersion,
    string holderName, out string? source, out string? error);
```

`source` is a nested static class holding `Regex Instance`, with the pattern's runner classes; `error` is
`TryCreate`'s message for a pattern that does not compile. The library's own source generator is built over the
same files, so there is one emitter with two callers. A test project takes the package from its `.nupkg` and
compiles it into a netstandard2.0 generator, to show it stands alone. A release of the library, before B.

**B. Corvus.JsonSchema: the adoption.**

1. **The dependency.** Corvus.Text.Json references Corvus.Regex.Ecma262 (net10.0 and netstandard2.0; the net9.0
   and netstandard2.1 builds take netstandard2.0's). The code generator and the Corvus source generator take the
   source package from A, so the emitter is compiled into each and neither loads another assembly.
2. **Edition and Unicode version.** By default, the grammar of ECMAScript 2020 for 2019-09 and 2020-12, which
   cite it, and today's grammar for draft 4, 6 and 7, OpenAPI 3.0 and 2.0. The Unicode version is V8's (17) for
   every draft. Both are overridden, each on its own: a CLI option, a source generator setting (an MSBuild property)
   and two properties of `JsonSchemaEvaluatorOptions`. A pattern compiles with the u flag, and falls back to the
   grammar without it, as today.
3. **Generated code.** The code generator emits the matcher from A into the generated type, from the CLI and from
   the source generator alike, for a type's own validation and for a precompiled program's pattern table. Today's
   emissions of .NET's `Regex` go from the generators.
4. **The runtime evaluator.** `PatternMatcher` holds a Corvus.Regex.Ecma262 `Regex` and matches the UTF-8 value
   directly. `RegexMatchTimeout` carries over as the pattern's match timeout. The library has no runtime-compiled form,
   so `CompileRegularExpressions` no longer selects anything; it stays, documented as having no effect.
5. **`format: regex`.** `JsonSchemaEvaluation.MatchRegex` asks the library whether the value is a valid pattern,
   under the same edition and version.
6. **Shape matchers.** The classifier in the code generator (`RegexPatternCategory`) and the kinds of
   `PatternMatcher` are each measured against the library on the evaluator benchmarks. A matcher stays only where
   it is faster; the rest go.
7. **No breaking change.** What takes .NET's `Regex` stays and keeps working, so code generated by an earlier
   version compiles and runs as before: `JsonSchemaEvaluatorOptions.RegexProvider` and its delegate,
   `JsonSchemaEvaluation.MatchRegularExpression(value, Regex, ...)` and `JsonSchemaEvaluator.ToDotNetPattern`, which
   keeps the translator in Corvus.Text.Json for it. Overloads and an option that take Corvus.Regex.Ecma262's `Regex`
   are added beside them, and the generators write those.
8. **Regenerated output.** The checked-in generated code (the OpenAPI, AsyncAPI and Arazzo models, the example
   recipes, the benchmark `C/` directories) is regenerated, and the recipes built and run.

**C. Corvus.JsonSchema: V4.** The V4 generators and runtime (`src-v4`, `Corvus.Json.*`) adopt the library the same way,
with no breaking change, after B.

## 3. Gates

- The JSON Schema Test Suite at every draft, with its optional `ecmascript-regex` and `non-bmp-regex`, and Bowtie,
  with nothing newly failing.
- The evaluator and generated-code benchmarks not slower, A/B against main.
- A test for each difference from today, written to fail before and pass after.
- The repository's pre-commit gates: a warning-free build, the affected tests, the code-sample catalog and the
  generated-code analyser configuration.

## 4. Your decisions

Taken: .NET first; edition by draft with overrides; V8's Unicode (17) under every grammar; the emitter as a source
package; shape matchers kept only where measured faster; generated code emitted through the library. B starts from
main in a worktree of its own.
